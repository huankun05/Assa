## 🔴 P0 阻塞项

### P0-1 · Part 4「嵌入 Hermes 核心」被严重低估，规模与文档描述不在一个量级

**问题**：文档 §9.3 把嵌入 Hermes 描述为"保留核心模块"，并把风险收敛为"唯一高风险改造点"。实测该代码本体量远非"模块"级别。

**实测证据**（源码位于 `D:/hermes_env/hermes-agent/`，MIT © 2025 Nous Research）：

| 文档声称要嵌入的模块 | 实际行数 |
|---|---|
| `hermes_state.py` | **13,114 行** |
| `run_agent.py` | **9,205 行** |
| `tools/approval.py` | 5,498 行 |
| `agent/prompt_builder.py` | 2,598 行 |
| `agent/memory_manager.py` | 1,291 行 |
| `toolsets.py` | 1,083 行 |
| **以上 6 项合计** | **≈ 32,789 行** |

全仓规模：**169,025 行 Python**；`tools/` 127 个文件、`agent/` 141 个文件、`gateway/` 54 个文件；`cli.py` 单文件 **1 MB**。

**影响**：
1. `run_agent.py`(9.2k 行) 与 `hermes_state.py`(13.1k 行) 是**子系统**而非模块，内部高度耦合（依赖其配置体系、`.env.example` 达 24KB、环境变量与全局状态）。"包一层拦截器"解决不了耦合。
2. 一旦 vendor 进来，就长期背负上游升级 / 安全修复 / 死代码负担，而我们只需要它能力的一小部分。
3. 我们的真实需求（单用户、仅 Windows、仅本地 Ollama、十几个工具）**远小于** Hermes 的设计目标（多 provider、多执行环境、多平台 gateway）。用 17 万行解决 1 万行的问题。

**建议（需你决策，二选一）**：
- **方案 A（文档现状）**：vendor Hermes 子集 + 冻结版本 + 记录 commit SHA。→ 起量大、周期长，但 LLM 调控/上下文压缩等难部件是现成的。
- **方案 B（推荐重新评估）**：**降级为"参考设计 + 自写精简 core"**，只 vendor 真正难写的一两块（如 `agent/context_compressor.py`），Agent 循环自写。→ 我们场景简单，可在几百行内跑通，且无上游负担、无耦合风险。
- **方案 C（折中）**：自写循环，但**直接复用** Hermes 的上下文压缩与 prompt 组装这两个"难且独立"的模块。

> 我的倾向：**C**。Agent 循环本身（接收→组装→调 LLM→解析工具→执行→回写）我们 200–400 行可自写且完全可控；上下文压缩是真难点，值得复用。

### P0-2 · 架构自相矛盾：语音层到底归 Rust 还是 Python？

**问题**：三处描述互相冲突，落地时必然扯皮。

- §3 架构图：把「语音输入输出 · TTS」画进 **「① 呈现层 · Rust+Tauri UI」** 盒子内。
- §6 技术栈：STT/TTS 定为 **faster-whisper / CosyVoice V3** —— 二者都是 **Python** 库，Rust 无法直接跑。
- §10.5：Rust 负责"托盘/热键/音频采集**播放**"，Python 负责 Agent 循环 —— **唯独没说 STT/TTS 推理归谁**。

**影响**：Phase 0 的第一个任务就是语音回路，这条边界不清会直接卡住目录与 IPC 设计。

**建议**：明确为——
- **Rust**：麦克风采集、扬声器播放、全局热键、托盘、单实例、沙箱执行。
- **Python sidecar**：VAD(Silero) / STT(faster-whisper) / TTS(CosyVoice) 推理 + Agent 循环。
- 并**同步修正 §3 架构图**：把 STT/TTS 推理移入 Python sidecar 盒，Rust 盒只留"采集/播放"。

### P0-3 · 权限闸存在安全缝隙：Hermes 的 Python 工具会绕过 Rust 沙箱

**问题**：文档两条铁律不能同时成立。

- §9.3 保留模块：`tools/`（127 个文件，**在 Python 进程内直接执行**文件读写与命令）。
- §9.3 Rust 沙箱：「所有"动手"操作最终由 **Rust** 执行，Python agent 只发"提议"」。

若 Hermes 的 Python 工具直接跑，就**根本没经过 Rust 沙箱**。而文档设计的"拦截器"只做 `policy.py` **裁决**（ALLOW/CONFIRM/DENY），**不做执行重定向** —— 裁决通过的工具仍在 Python 里执行。这是文档目前最大的安全洞。

**建议**：补一张**执行路由表**（这是缺失的关键设计）：

| 工具类别 | 例子 | 执行位置 |
|---|---|---|
| 只读 | `fs.list` / `fs.read` / `fs.search` / `sys.status` / `calendar.q` | Python 内直接执行（过 policy + 安全区范围校验） |
| 写 / 执行 / 网络 / 凭据 | `fs.trash` / `fs.move` / `shell.run` / `browser.auto` / `msg.send` | **序列化为 IPC → Rust 沙箱执行**（Python 只发提议） |

并明确：**审计日志由 Rust 独占 append-only 写入**（Python 可篡改自己的日志，审计就失去意义）。

## 🟠 P1 重要项

### P1-1 · Part 6 前提被误述：desk-pet 的记忆 embedding 目前是**非语义**的

文档 §10.6 写「本地 Ollama nomic-embed-text 主 + 云端兜底」。但复用 desk-pet 引擎**不会自动得到**这个能力：

- `embedding.py` 的 `get_embedder(provider="local_hash")` **只支持 `local_hash`** 一种，其余直接 `raise ValueError`。
- 默认实现 `LocalHashEmbedder` 是 **MD5 特征哈希**（384 维，字符 + 2-gram），注释自述「适合关键词/短句的近似匹配」。
- `nomic_embed_text` / `openai` / `ollama_generic` 在 docstring 中仅列为「**后续可扩展**」，**未实现**。

**影响**：照搬即得到"关键词近似匹配"的记忆 —— "重启电脑" 和 "重新启动机器" 匹配不上，"越来越懂你" 会明显打折。

**建议**：把「自写 `OllamaEmbedder`」明确列入 Part 6 工作量。模型已就绪：`nomic-embed-text`（274MB，已装）；中文更强可选 `bge-m3`（1.2GB，已装）。

### P1-2 · `policy.py` 只焊了一半闸门：scope / 批量上限 / 回收站均为死数据

- `decide()` 的 `params` 参数**完全未被使用**；`ToolMeta.scope` 字段声明了但**从不参与判定**。

**影响**：看起来有闸，实际闸门只焊了一半 —— 安全区范围限制形同虚设。

**建议**：Phase 1 前补全 `decide()` 的 scope 校验（传真实路径 → 比对安全区白名单）、批量上限入 schema、回收站标记入执行层。
