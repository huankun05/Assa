## 🔴 P0 阻塞项

### P0-1 · 权限裁决权归属三处矛盾（安全架构必须先定）

同一问题在三处有三种说法：

| 位置 | 说法 |
|---|---|
| `src-tauri/README.md` 第 8 行 | **Rust** 做"权限闸策略引擎：加载 schema，裁决 allow/confirm/deny" |
| 设计文档 v1.1 §5.2 / §3.2 | **`policy.py`（Python）裁决**，Rust 只执行 |
| `agent/gate/policy.py` docstring | "Rust 后端在 Phase0 后会用同一份 schema **复刻此逻辑**" |

**为什么这不是小事**：若 Rust 只执行不复核，那么 Python 侧被提示注入或出 bug 时，可以直接发 IPC"执行这条命令"绕过一切——整个权限闸形同虚设。安全架构的**正确答案只有一个**：

> **双闸门，Rust 为最终权威**：
> - `policy.py`（Python）= **提议侧预检**：避免提出必被拒的请求、知道何时该弹确认 UI（用户体验层）。
> - Rust 侧闸门 = **终审**：执行前用同一份 `tool_schema.json` 复核，不符一律拒绝（安全边界层）。
> - 两份逻辑共享同一 schema 单一事实源；审计日志只由 Rust 写。

需要同步修改：设计文档 §3.2/§5.2 表述、两处 README。

### P1-2 · `agent/memory/store.py` 与设计冲突（两处）

1. **路径冲突**：`DB_PATH = <repo>/data/memory.db`，而 v1.1 §7.1 锁定数据目录为 `%APPDATA%\assa\`（config / memory.db / audit.log / logs）。repo 内 `data/` 是开发期临时做法，须定"路径解析函数"统一收口（开发期可用环境变量覆盖）。
2. **表结构冲突**：stub 表只有 `kind/content/embedding`，**没有 `layer`（L0–L3）与 `category` 字段**——而锁定决策是复用 desk-pet 的分层引擎（`MemoryFragment` 带 layer+category）。接 desk-pet 引擎时此 stub 会被替换，但应提前在 README/docstring 标注"Phase 2 将整体替换为 desk-pet 分层引擎"，避免误以为在此 stub 上演进。

### P1-3 · 音频采集归属与依赖矛盾

v1.1 §3.1 锁定：**Rust 负责麦克风采集/扬声器播放**，Python 只做推理。但 `voice/requirements.txt` 里有 `sounddevice>=0.4.6`（Python 音频采集库）——即 stub 是按"Python 采集"写的。

**建议**（二选一，写死即可）：
- **A（贴 v1.1）**：Phase 0 就让 Rust 采集，音频流走 IPC 给 Python；从 requirements 移除 sounddevice。
- **B（务实降级）**：Phase 0 先用 Python sounddevice 打通回路（少写一层 IPC），**Phase 1 再把采集移到 Rust**；requirements 保留但在 README 标注是过渡方案。
> 倾向 B：Phase 0 的目标是验证"延迟与住进来的感觉"，少一层 Rust↔Python 音频流 IPC，风险更小。

### P1-4 · CosyVoice 集成路径未定义

`voice/tts.py` 注释"调用你已部署的 CosyVoice V3（本地）"、requirements 注释"你本地已装，走已有环境"——但 CosyVoice **不在 pip 上**（GitHub 项目，依赖 modelscope/torch），"走已有环境"到底是：HTTP API 调用？子进程？还是把模型装进本项目 venv？三者的资源占用、延迟、打包方式完全不同。

**建议**：设计文档补一节。鉴于纳西妲 TTS 项目已有 CosyVoice 部署，**推荐 HTTP 服务模式**（汐月作为客户端调用），解耦模型生命周期（显存不用即卸载的习惯不受影响），也符合 Phase 0 先用 Kokoro 打通、CosyVoice 后接的计划。
